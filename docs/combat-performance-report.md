# Отчёт по производительности боя

## Окружение

- Godot: 4.7.1 stable official, headless, `gl_compatibility`.
- ОС: Microsoft Windows 10 Pro 64-bit, 10.0.19045.
- CPU: AMD Ryzen 7 7700X, 8 ядер / 16 логических процессоров.
- GPU: AMD Radeon RX 6700 XT, драйвер 32.0.21043.10005. В headless-запуске Godot не вернул имя видеоадаптера, поэтому GPU не считается участником замера.
- Physics tick: 60 Гц; бюджет physics-кадра — 16,67 мс.
- Проектное разрешение: 1280×720.
- Seed: `123456`.
- Длительность каждого замера: 3 секунды после 30 прогревочных physics-кадров, 180 измеряемых кадров.

## Методика

Benchmark создаёт настоящие сцены врагов и `EnemyProjectile`, регистрирует их в `WorldState` и оставляет активными AI, movement, obstacle queries, separation, spatial updates и projectile movement. Герой неподвижен и неуязвим, волны и генерация локации отключены. Снаряды получают тангенциальное направление, чтобы не исчезать сразу после старта.

FPS рассчитывается по wall-clock интервалу между physics-кадрами. Physics time читается из `Performance.TIME_PHYSICS_PROCESS`. На Windows планировщик иногда даёт редкие длинные интервалы, поэтому для оценки нагрузки важнее средний physics time, а minimum FPS используется как индикатор выбросов.

Baseline снят до оптимизаций. Optimized снят после всех низкорисковых изменений той же сценой, с тем же seed и теми же параметрами.

## Сравнение

| Профиль | Изменение avg physics | Изменение min FPS | Вывод |
|---|---:|---:|---|
| 100 / 100 | +4,4% | −0,04% | Разница мала; выигрыш не доказан одним коротким прогоном. |
| 200 / 300 | +3,6% | −0,2% | Среднее осталось внутри бюджета 16,67 мс, но небольшой профиль не ускорился. |
| 500 / 1000 | −6,6% | +33,2% | Средняя стоимость снизилась, но профиль всё ещё не укладывается в 60 Гц. |

Пиковый physics time вырос во всех трёх повторных профилях. Это значит, что текущий PR уменьшает часть постоянной нагрузки на большой толпе, но не устраняет источники редких тяжёлых кадров. Память выросла примерно на 1–2% из-за caller-owned scratch buffers у живых сущностей.

## Выполненные оптимизации

1. `PlayerHero` и `EnemyBase` больше не вызывают redraw безусловно каждый physics tick. Перерисовка зависит от направления, hit-flash и активной анимации.
2. Dash HUD ограничен 20 обновлениями в секунду и получает немедленные события смены состояния.
3. Enemy separation распределён по трём фазам и переиспользует последнюю коррекцию. В отдельном сравнении на 500/1000 divisor 2 дал 22,390 мс и 31 пересекающуюся пару, divisor 3 — 20,132 мс и 26 пар; выбран divisor 3.
4. SpatialGrid получил `query_into`; горячие вызывающие системы переиспользуют собственные typed buffers.
5. Проверки препятствий и свободной позиции используют squared distance там, где длина не нужна.
6. `PlayerAttack` конфигурирует `AttackShape` и считает урон один раз на сегмент, затем выполняет дешёвый radial broadphase до точной swept-circle формулы.
7. Добавлен input buffer меча на 0,12 секунды. Это улучшение отзывчивости, а не производительности.

## Оставшиеся bottleneck

- Профиль 200/300 стабилен в бюджете 60 Гц; обязательной центральной crowd-системы для текущего игрового лимита 120 врагов нет.
- Профиль 500/1000 превышает бюджет примерно в 1,5 раза. По промежуточным измерениям separation является заметной частью стоимости, но финальный benchmark не содержит per-function profiler, поэтому считать его единственной причиной нельзя.
- 1000 снарядов — это 1000 `Node2D` с отдельным `_physics_process`, spatial update и draw state. Вероятный следующий источник стоимости — число GDScript/Node вызовов; это вывод по архитектуре, а не измеренный процент.
- Пики max physics требуют отдельного profiler capture. Возможные причины: массовые переходы между grid-ячейками, одновременные attack/cast состояния и освобождение большого числа Node.
- Scratch buffers устранили временные result arrays, но постоянные buffers на каждом враге увеличили память. Для реального лимита 120 врагов это приемлемый обмен; на 500+ стоит сравнить один централизованный buffer на системный проход.

## Оценка следующих изменений

- `CrowdSystem`: пока не обязателен для 200 врагов; становится следующим кандидатом, если целевой дизайн требует стабильные 500.
- Projectile pooling: рекомендуется отдельным следующим PR после замера spawn/despawn-пиков; особенно полезен для магов и профиля 1000 снарядов.
- Enemy pooling: пока не требуется; применять только если profiler покажет пики создания/удаления волн.
- ECS: не требуется для текущего лимита и не должен быть следующим шагом.
- Data-oriented combat layer: рассматривать только при подтверждённой цели 500+ одновременно симулируемых врагов после CrowdSystem и pooling.

## Запуск benchmark

Из корня проекта:

```powershell
godot --headless --path . res://scenes/debug/combat_benchmark.tscn -- --benchmark-enemies=200 --benchmark-projectiles=300 --benchmark-duration=3
```

Дополнительный параметр для сравнения separation:

```powershell
--benchmark-separation-divisor=2
```

Поддерживаемые контрольные профили: `50/100`, `100/100`, `200/300`, `500/1000`. Результат печатается строкой `COMBAT_BENCHMARK` в JSON.
